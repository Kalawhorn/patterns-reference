What to focus on

19 study days, then the interview. Arrays and hash maps are already comfortable, so the time goes to graphs, trees, search, heaps, backtracking and DP. The goal is not a problem count. It is this: see an unfamiliar prompt, name the structure underneath it, state a baseline, derive something better, write clean Python, and test it out loud.

The one habit worth drilling every dayBefore you write a line, finish one sentence — “dfs(node) returns…”, “the window always contains…”, “lo is the smallest value that could still be the answer”. Google is scoring the reasoning. A stated invariant is the cheapest possible evidence of it.

Where the hours go

Tier 1~half your time

Graphs and trees. Grid and adjacency traversal, BFS by levels, topological sort, Dijkstra. Tree recursion, level order, BST bounds, lowest common ancestor.

This is the bulk of what Google actually asks, and it is where your prep gap is. Everything in tier 2 shows up wrapped in one of these.

Tier 2~a third

Binary search on an answer, heaps and top-K, intervals and greedy, backtracking with pruning.

High frequency, small surface area. Each is one template plus one invariant you have to say out loud.

Tier 3the rest

DP and Union Find — recognise and implement the common shapes only. Take-vs-skip, prefix feasibility, two-sequence DP. Union Find for “edges arrive one at a time”.

Worth being unsurprised by. Not worth becoming a specialist in with 19 days on the clock.

Skipdeliberately

Minimum spanning trees, tries beyond the basics, segment trees, KMP and friends, bit tricks, Hard DP.

Low probability at L4, and every hour here is an hour not spent on tier 1. If one appears, modelling the problem clearly will earn more than a half-remembered algorithm.

The other half of the score

  • Narration. Clarify, baseline, invariant, code, walk through, complexity, follow-up — in that order, every time. An unspoken correct approach scores below a spoken one.
  • Follow-ups. Google interviewers change the question. After every solved problem, answer one out loud: what if the weights weren’t equal? what if the input didn’t fit in memory? what if duplicates were allowed? what if the tree had cycles? Two minutes, every problem. This is the L4 differentiator and it costs almost nothing.
  • Recovery. Being wrong and catching it yourself reads as strength. Practise saying “that duplicates queue entries — I should mark seen on enqueue instead” rather than silently editing.
Not covered hereThis plan is coding rounds only. The loop also has a Googleyness / behavioural round, and it is scored. Study firstfind and union, with path compression
python
parent = list(range(n))
rank = [0] * n

def find(x):
    if parent[x] != x:
        parent[x] = find(parent[x])   # path compression
    return parent[x]

def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb:
        return False                  # already connected -> this edge is a cycle
    if rank[ra] < rank[rb]:
        ra, rb = rb, ra
    parent[rb] = ra
    if rank[ra] == rank[rb]:
        rank[ra] += 1
    return True

The idea

A subtree is a smaller copy of the whole tree, which is why recursion feels natural here. The only real decision is what one call hands back to its caller. Finish the sentence “dfs(node) returns ___” before you type anything; almost every bug on this day is a fuzzy answer to that question.

Two different jobs a recursion can do

  • Return information upward. Height, size, sum — the caller uses the value.
  • Update an answer as a side effect. The recursion is really a traversal, and the answer accumulates in a variable outside it.

104 and 226 only need the first. 543 needs both at once, and that is the whole reason it is on today’s list.

Traps

  • Guarding things that are already safe. if node.left or node.right: around a swap protects nothing — swapping None with None is a no-op, and recursing into None hits the base case. The guard that matters is if not node:, which stops the dereference.
  • Pushing the answer downward as a parameter. A parameter is a fresh local in every frame; writing to it changes nothing for the caller. Results travel up via return values, or sideways via a nonlocal / self. variable.
  • Mixing edge counts and node counts. Height in edges gives leaf → 0; in nodes it gives leaf → 1. Both are workable. Pick one, write it in a comment, don’t switch mid-problem.
  • A helper that re-walks what the caller already walked. If computing the answer at each node costs a full subtree scan, you have turned O(n) into O(n²) — every node is re-visited once per ancestor.

Problem by problem

  • 104 Maximum Depth — the return value is the answer. The cleanest possible version of the pattern.
  • 226 Invert Binary Tree — local work at every node, then recurse. Order does not matter: swapping a node’s children and inverting each subtree are independent, so swap-then-recurse and recurse-then-swap agree.
  • 110 Balanced Binary Tree — reinforce — height again, but the answer is a yes/no condition checked at every node. The dry run for 543: same walk, different thing recorded.
  • 543 Diameter — the return value is not the answer. Return the height; while you have both child heights in hand, record left + right as a candidate. One pass, O(n) time, O(h) stack.

Say this

“height(node) returns the number of edges below the node. The diameter through any node is left height plus right height, which I already have while computing the height — so I record it as I go rather than re-walking the subtree.”

Done when

You can state the return value before writing the function, and derive 104 from a blank file in about five minutes.

The idea

Three different shapes of tree reasoning, and the point is telling them apart: traverse by level (BFS), carry constraints downward (BST bounds), or combine what the two subtrees report back (LCA). Choose based on what the problem asks for, not on which one you like.

Traps

  • Forgetting the level-size loop. for _ in range(len(q)) must be read before you start appending children, otherwise the level boundary dissolves. Capture the length first.
  • Validating a BST with parent–child comparisons. Every node must sit inside a range set by all its ancestors. A node can be larger than its parent and still be illegal because some grandparent already capped it.
  • Using <= where the problem says strict. Duplicates are the classic BST edge case — ask about them.
  • Hunting for parent pointers in LCA. You do not have them and you do not need them.

Problem by problem

  • 102 Level Order — the canonical BFS shape. Everything later with “per level” in it reuses this loop.
  • 98 Validate BST — pass (low, high) down; start with -inf, inf; going left tightens the high bound, going right tightens the low one.
  • 103 Zigzag Level Order — reinforce — the 102 loop unchanged; only the order you record each level flips. Reverse the level list, never the queue.
  • 236 LCA — return the node itself when found, None when not. If both sides return non-None, this node is the answer; if only one does, pass it up. Read that rule twice — it is the entire solution. KEY: check if node is p or node is q: return node BEFORE recursing to children. This catches targets that ARE the node itself, and seeds the recursion.

Say this

“lca(node) returns the target if the subtree contains one target, and the answer if it contains both. Two non-null children means the split happens here.”

The idea

Tree recursion generalises to graphs by adding one thing: a visited set. Trees cannot revisit a node; graphs can, and a grid can revisit from four directions at once. A matrix is a graph whose edges you generate arithmetically instead of storing.

Traps

  • Marking too late. Mark a cell visited before recursing into its neighbours, or two neighbours will each queue the other and you will walk in circles.
  • Bounds after the lookup. Check 0 <= r < rows before touching grid[r][c]. Negative indices do not raise in Python — they silently wrap to the other edge, which is a wrong answer, not a crash.
  • Counting components wrong. The outer loop starts a DFS at every unvisited cell; the counter increments once per start, not once per cell.
  • Mutating the input without saying so. Sinking islands by overwriting the grid is fine and O(1) extra space — but ask permission out loud, then mention the visited set as the non-destructive alternative.

The idea

BFS finishes distance 0, then distance 1, then distance 2 — so the first time it reaches a node is by a shortest path, provided every step costs the same. That guarantee is the entire reason to prefer it over DFS here, and it is what you should be able to explain in plain English by tonight.

Traps

  • Marking seen on dequeue. Mark on enqueue. Otherwise a node can be queued several times before it is first processed, and the queue blows up.
  • Using a list as a queue. list.pop(0) is O(n) and quietly turns the whole search quadratic. deque.popleft() is O(1).
  • Counting the wrong thing in multi-source BFS. Every source starts at distance 0 together; the layer counter increments once per level, not once per node.
  • Rotting Oranges’ empty case. No fresh oranges at the start means the answer is 0, not −1. Check the leftover count at the end, not during.

The idea

Dependencies are directed edges. Indegree counts how many prerequisites a node is still waiting on; a node with indegree zero is runnable right now. Repeatedly removing runnable nodes either drains the graph (a valid order exists) or stalls (a cycle).

Traps

  • Edge direction backwards. LeetCode gives [course, prereq]. The edge points prereq → course, because finishing the prereq is what unlocks the course. Say the sentence out loud before you build the list.
  • Detecting the cycle with a visited set. With Kahn you do not need one: if len(order) < n, something never reached indegree zero, and that is your cycle.
  • Decrementing more than once. Each edge is relaxed exactly once, when its source is dequeued.

The idea

A heap gives you “the smallest thing, repeatedly” in O(log n). Dijkstra is BFS with a heap instead of a queue: when steps cost different amounts, the frontier has to be explored cheapest-first rather than in insertion order.

Traps

  • Forgetting heapq is a min-heap. For the largest values, push -value and negate on the way out.
  • Comparing tuples that contain incomparable objects. Ties fall through to the next element, so (dist, node) is fine for ints but blows up for custom objects. Add a tiebreaker index if needed.
  • Not skipping stale entries. You may push the same node several times. On pop, if the popped distance is not the best known one, continue.
  • Reaching for Dijkstra when BFS would do. Equal weights → BFS. Negative weights → neither; that is Bellman–Ford, and worth naming as a follow-up.
  • Heap size for top-K. Keeping a min-heap of size k gives O(n log k); sorting everything is O(n log n). State which you chose and why.

  • 1514 Max Probability — transfer test: maximise a product instead of minimising a sum. Push negated probabilities and the same algorithm works.

“With equal weights BFS is enough. Once edges cost different amounts, insertion order stops matching cost order, so I use a priority queue to always expand the cheapest known frontier node.”

The idea

Sorting converts a two-dimensional mess into a one-pass scan. Once intervals are ordered by start, the only thing you ever compare against is the last interval you kept — everything earlier is settled. Greedy works when you can argue the local choice never costs you globally.

The idea

Binary search is not about arrays. It is about a predicate that flips exactly once: false, false, false, true, true. Find the flip. If you can define feasible(x) and argue it is monotonic, you can binary search a range of answers that was never stored anywhere.

Traps

  • Undefined boundaries. Write what lo and hi mean before the loop. Nearly every off-by-one here is a fuzzy definition, not a typo.
  • Mixing loop styles. while lo < hi with hi = mid converges on a boundary. while lo <= hi with hi = mid - 1 searches for an exact hit. Pick one shape and keep it.
  • Infinite loops. If a branch does not shrink the range, you never terminate. lo = mid + 1 must be the branch that excludes mid.
  • Rotated arrays: comparing the wrong pair. Compare nums[mid] against nums[lo] to decide which half is sorted, then check whether the target sits inside that sorted half.
  • Search space bounds. For Koko, lo = 1 and hi = max(piles). Starting at 0 gives a division by zero.

The idea

Backtracking is a decision tree walked depth-first. Four things define it, and if you name all four before coding, the code writes itself: state, choices available from that state, completion condition, undo.

Traps

  • Appending the path without copying. result.append(path) stores a reference; every entry ends up identical (and empty). Use path.copy().
  • Forgetting the undo. Every append before the recursive call needs a matching pop after it, or the next sibling branch inherits your choices.
  • Duplicate results from the wrong loop start. Subsets and combinations pass i + 1 (or i, when reuse is allowed) to stop revisiting earlier elements. Permutations instead track which values are used.
  • Not knowing the cost. Subsets is O(n · 2ⁿ), permutations O(n · n!). Say the number of results out loud — it explains why no polynomial solution exists.

Problem by problem

  • 78 Subsets — every node of the recursion tree is an answer, so record on entry rather than at a base case.
  • 46 Permutations — choices come from unused values, not from an index that only moves forward.
  • 77 Combinations — reinforce — 78 with a completion condition. You record only when the path reaches length k, which forces you to separate “record” from “recurse”.
  • 39 Combination Sum — add a remaining-target to the state; passing i rather than i + 1 is what allows reuse. Stop the branch when the remainder goes negative.

Say this

“State is the path plus the index I’m allowed to start from; choices are the remaining candidates; I’m complete when the target hits zero; and I undo with a pop so the next branch starts clean.”

Done when

You name state, choices, completion and undo out loud before typing — four sentences, then code.

The idea

Pruning is what separates backtracking from brute force: prove a partial state can never become valid, and cut it before recursing. The strongest version does not generate the bad branch at all.

Traps

  • Validating at the end instead of the edge. Generate Parentheses is the model — it never produces an invalid prefix, because a close is only offered while closed < opened.
  • Forgetting to restore a grid cell. Mark, explore, then put the original character back. Miss the restore and later paths see a corrupted board.
  • Restoring on the wrong path. The undo has to run whether the branch succeeded or failed — keep it on the line after the recursive call, not inside an if.
  • Skipping the cheap first check. In Word Search, bail immediately when the cell does not match word[i]; that single line removes most of the tree.

The idea

The idea

Union Find answers one question fast: are these two already connected? Use it when edges arrive over time and you need connectivity maintained incrementally. If the graph is fixed and you just need reachability once, plain DFS or BFS is simpler — knowing which situation you are in is the point of today.

Traps

  • Comparing nodes instead of roots. Every check goes through find. Two nodes are connected when their roots match.
